This page is about this repository's own `spec` workflow, not about running e2e in your CI. A red `spec gate` must mean the change is broken, that a listed flake failed its one retry, or that the run never reached a test. The matrix runs five Node slots on shared runners, and that shared infrastructure exposes a small set of failures that are not defects in the change. This page defines the three kinds with their evidence, the retries the gate allows, and which runs count toward #25's three independent runs.

## Three kinds of failure

| Kind | When it is this | What happens |
| --- | --- | --- |
| Deterministic failure | It repeats on the same head with the same shape, and the shape names a code or config cause. | Fix it. It is never listed and never retried. |
| Known flake | It appears only in the multi-slot matrix, does not reproduce on its own, its shape is resource or timing contention, and its evidence shows it is unrelated to product semantics. Tests ran in this case. | Listed in `scripts/ci/known-flakes.json`; the slot gets one retry. |
| Infrastructure failure (tests did not execute) | The run failed before a test started: a runner was never acquired, or a setup step failed, and its log names a concrete environment error. | Not a test failure and not retried by the slot retry. One manual rerun of the failed jobs is allowed. Never counts as one of #25's three independent runs. |

A failure that is not in the list stays red, even when it looks like one of the known shapes. That is the point: the list is a closed set, not a pattern for "probably flaky", and the infrastructure kind is not a label for "the job looked odd".

## Telling an infrastructure failure from a test failure

All three checks must hold. The spec gate performs them for every failed job that runs tests and prints the result; the same procedure is what a person applies when reading a run.

1. **No test executed.** Read the failed job's steps. The step that runs tests is `Unit and integration tests` in a `test (<node>)` slot, `Testbed` in `check`, and `Run the reference consumer matrix with exact counts` in `consumers`. When that step ends `success` or `failure`, tests ran, and the failure is a test failure. When it is `skipped`, or the job has no steps at all, no test started. A build that fails inside the test step counts as executed and is a code failure.
2. **The first failed step is environment bootstrap, not the test step.** In a test slot that is `Set up source-pinned native runtime` or `Install browsers`; `check` and `consumers` fail in the same setup step before their test step. A job cancelled while waiting for a runner has no steps at all.
3. **The log names a concrete environment error registered in the list.** The first failed step must match an infrastructure entry's `step`, and the job log must match its `patterns`. Run `43020654584` attempt 2 is the reference: the step is `Set up source-pinned native runtime`, and the log carries `Temporary failure resolving 'azure.archive.ubuntu.com'` after the `Ign:` retries of the four `noble` suites.

When checks 1 and 2 hold but 3 does not, the failure is **unclassified**: still red, still not evidence, and a defect to fix. So is a failure caused by repository content, such as a bad native pin, a malformed artifact manifest, a failing `Lint` or `pnpm install --frozen-lockfile`, or a build that fails inside the test step: no test ran, but the cause is ours. None of these is infrastructure, and one observation of a new error is a defect to ticket, not an entry to add in the same pass.

## Retry and counting

- **No automated retry for this kind.** `scripts/ci/flake-retry.mjs` reruns a slot's failed test files; an infrastructure failure has none. The gate never retries it.
- **One manual rerun per head.** Re-run the failed jobs once. The rerun is a new attempt of the same run and is classified the same way. If the rerun fails the same way, the one rerun is spent: do not rerun again. The failure is then either a repository input to fix or an external outage to record as not evidence.
- **It does not count toward #25.** A run in which tests did not execute is not one of the three independent runs, whether the gate ended red or green. Record it in the evidence as "tests did not execute" and rerun; only runs where the tests actually ran count.
- **The gate stays red.** The classification explains the failure and marks the attempt; it never turns a job green.

## Reading the gate summary

`spec gate` prints two tables. The per-slot table has a `failure kind` column: `test`, `infrastructure (tests did not execute)`, or `unclassified (tests did not execute)`. The failed-jobs table names every failed job that runs tests, its kind, the first failed step, and either the registered signature that matched or the reason it did not. An infrastructure row is also announced with a warning on the run, so the attempt is marked as not evidence even though the gate is red.

## The retry

A failed slot may be retried once, under all of these conditions:

- Every failed test file in the slot has a failure block that matches a listed signature. One unlisted failure cancels the retry.
- The log's own failed-test and failed-file totals match the failing tests the summary names. A file that failed to collect has no `FAIL ...test.ts` line, so a mismatch cancels the retry.
- The slot did not already end red with a listed signature on the previous completed run at the same head. That second consecutive failure is deterministic: the gate stays red and the failure gets a ticket.
- The retry reruns the failed test files and the root `test` chain's commands after the web package, through the same pinned-native fixture wrapper as the first attempt. The first attempt is an `&&` chain: a failure in e2e or web stops it, so the later packages never ran, and a retry of the failed file alone would hide them.

A passed retry makes the slot green. A failed retry leaves it red, and so does an unlisted signature. `spec gate` prints one audit table with the slot that retried, the signature the first attempt failed on, and the retry result; the same details live in the slot artifact (`spec-retry-<node>.json` and its log). No retry is silent.

The retry never runs for a slot that never started, for an infrastructure failure (no failed test file exists), for a collection error with no failed test file or one the log's totals cannot account for, or when the previous completed run at the same head left that slot red under a listed signature.

## Register a new flake

1. Collect the evidence: the run id and matrix slot, the exact failure block, the test, how often it appeared, and the proof that it is not a product defect. A single observation is not enough; the same signature must have recurred across runs or heads.
2. Add the entry to `scripts/ci/known-flakes.json`: a stable `id`, the smallest regex that matches the observed failure block, and the evidence object. Patterns are anchored to the failure text; do not use a bare word that a product assertion could quote.
3. Open a pull request and update this page's table in the same change.
4. Review the list in the pull request that follows a release or a CI change. Remove an entry whose signature stopped appearing or was fixed; add every new signature with its evidence.

An infrastructure entry uses the same file with `kind: "infrastructure"`, a `phase`, `testsExecuted: false`, and the proof that no test started. An entry `spec gate` sees also carries the `step` it fails in and the log `patterns` that confirm the environment error; one outside `spec gate`, like the macOS capacity entry, sets `gateVisible: false` and is read from the run record instead. It does not need the recurrence a flake needs, because the error is outside the repository: the entry must show the same repository state passing around the failure (a sibling job in the same attempt, the producer job, or the previous attempt at the same head). A setup failure caused by repository content is not this class and goes to an issue. A deterministic failure is fixed or tracked with its own issue. It never becomes a listed flake.
